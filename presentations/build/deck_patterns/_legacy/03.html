Manufacturing IoT: the bucket that marches to 16 MB

Sensor readings are bucketed per machine, per hour to keep document counts down. It's the canonical write-amplification pattern: every reading $push-es into the bucket and re-serializes it — and hot sensors march the bucket toward the hard cap.

Document — the bucket grows, the write cost grows with it

db.readings.updateOne(
  { machine: "M-118", hr: "2026-09-25T14" },
  { $push: { pts: { t: ts, v: 71.4 } },
    $inc:  { n: 1 } }
)
// each push re-serializes the whole bucket;
// a busy sensor hits the 16 MB doc cap and
// analytics can't scale past one bucket.

Converged — partitioned relational time-series

-- readings: RANGE-partitioned on ts, auto-interval
SELECT /*+ PARALLEL(8) */ machine_id,
       TRUNC(ts,'HH') AS hour,
       AVG(val), MAX(val), COUNT(*)
FROM   readings
WHERE  ts >= SYSTIMESTAMP - INTERVAL '7' DAY
GROUP BY machine_id, TRUNC(ts,'HH');
-- append-only inserts; no cap, no re-serialize.

Value-add — $sql in the pipeline: a document team keeps its aggregation pipeline and drops full SQL — parallel scan, window functions, joins — into one $sql stage. The heavy analytic that timed out as a pipeline runs to completion with no 16 MB / 100 MB pipeline caps. Scale-out parallelism, mid-pipeline.

The needle flips on the hottest sensors — exactly the ones you care about. Append-only inserts have flat write cost; the rollup is a GROUP BY over a partition range, parallelized by the optimizer, not by you.
