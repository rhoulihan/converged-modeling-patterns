Act 3 · Pattern 4 — Subset0:50 – 0:55

Insurance: the recent-claims subset nobody reads

A policy document keeps the 10 most recent claims inline for a fast summary; cold history lives elsewhere. Claims arrive constantly, so you push-and-trim on every write — to serve a full read that happens rarely.

Document — maintain the subset on every write

db.policies.updateOne(
  { _id: "P-42" },
  { $push: { recentClaims: {
      $each:  [ newClaim ],
      $sort:  { ts: -1 },
      $slice: 10 } } }   // trim to 10
)
// write amplification on the write path to
// optimize a read path that's mostly idle.

Converged — stop maintaining it; query it

-- composite index: (policy_id, event_ts DESC)
SELECT claim_id, amount, event_ts
FROM   claims
WHERE  policy_id = :id
ORDER BY event_ts DESC
FETCH FIRST 10 ROWS ONLY;
-- index-only, O(log n) seek + 10-row scan.
-- a duality view reunites hot + cold on read.

Subset is a bet that reads dwarf writes. When they don't, you're paying the write side to optimize a read that hardly fires. A pre-sorted composite index gives the same instant Top-N with zero write-path cost.

Pattern 4, Subset — the sharpest 'you're paying the wrong side' story. Keep it tight.

▸ The setup: a policy doc keeps the 10 most recent claims inline for a fast summary; cold history lives elsewhere. Claims arrive constantly.
▸ The hard edge (hot SQL): $push with $sort + $slice:10 on EVERY write — write amplification on the write path to optimize a read path that's mostly idle.
▸ The softening (cool SQL): stop maintaining it. A composite index (policy_id, event_ts DESC) makes ORDER BY event_ts DESC FETCH FIRST 10 an index-only seek + 10-row scan. A duality view reunites hot + cold at read time.

Land: Subset is a bet that reads dwarf writes. When they don't — and here they don't — you're paying the write side to optimize a read that hardly fires. The pre-sorted index gives the same instant Top-N at zero write cost.
