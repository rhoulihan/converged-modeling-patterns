Manufacturing: the bill of materials you have to re-parent

A BOM stored as a materialized path makes "everything under this assembly" a fast prefix scan. Then engineering re-parents a subassembly — and you rewrite the path of every descendant. And "which assemblies use part X?" a prefix can't answer at all.

Document — re-parent rewrites the whole subtree

// move subassembly SA-7 under A-2:
db.bom.updateMany(
  { path: /^root\.A-1\.SA-7/ },
  [ { $set: { path: { $replaceOne: {
        input: "$path",
        find:  "root.A-1.SA-7",
        replacement: "root.A-2.SA-7" } } } } ]
)  // write amp ∝ size of the subtree

Converged — trees stay cheap, graphs become possible

-- explosion: every descendant of an assembly
SELECT part_id, LEVEL depth FROM bom
START WITH parent_id = :asm
CONNECT BY PRIOR part_id = parent_id;

-- reverse, N-hops: which assemblies use a part?
SELECT * FROM GRAPH_TABLE ( bom_graph
  MATCH (p) <-[:USED_IN]-{1,} (a)
  WHERE p.part_id = :part
  COLUMNS (a.part_id) );
-- re-parent = ONE edge update.

A path encodes one traversal direction and pays to maintain it. Split the concern: let the tree be edges (re-parent is a single row), and let genuine graph questions be graph queries — the prefix trick never could express them.

Pattern 5, Tree — two failures in one: re-parent write amplification AND a question the model can't express. Make both.

▸ The setup: a BOM as a materialized path makes 'everything under this assembly' a fast prefix scan.
▸ Hard edge #1 (hot SQL): re-parent a subassembly and you rewrite the path of EVERY descendant — write amp proportional to subtree size.
▸ Hard edge #2: 'which assemblies USE part X?' is the reverse direction, N hops — a prefix simply cannot express it. You'd denormalize a second structure.
▸ The softening (cool SQL): CONNECT BY for the explosion; GRAPH_TABLE with a {1,} quantified pattern for the reverse traversal. And re-parent becomes ONE edge update.

Land: a path encodes one traversal direction and pays to maintain it. Split the concern — tree as edges (re-parent = one row), genuine graph questions as graph queries. The prefix trick never could answer the second question at all.
